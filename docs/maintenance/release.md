# 推送与发布

推送代码和发布版本是不同动作；只执行当前任务授权的部分。开始前重读对应步骤，不能凭上次经验跳过清单。

## 1. 推送代码

1. 读取 [质量审查](review.md)，确认适用门禁、隐私检查和审查结论。查看工作区及暂存差异，明确本次只包含哪些文件。
2. 通过远端地址确认目标是本项目。获取目标主分支，比较自任务起点以来的**全部变化**，特别是网页端直接修改的主页和文档；不能只通过提交标题判断。
3. 在本项目主分支历史上工作时，正常合并或变基远端新增改动，处理冲突后复验，再进行快进推送。贡献者走合并请求；维护者得到授权时可直接推送主分支。
4. 如果内核开发分支携带上游历史，而发布库采用独立历史，先在发布库主分支上制作可审查的应用结果，逐项保留远端改动。先比较远端内容、候选内容与共同内容基线，逐项处理新增和冲突；不得直接把候选树嫁接到远端父提交而跳过内容合并。
5. 推送后核对远端提交编号和持续集成作业确实对应本次提交。权限、网络或竞争性更新阻止推送时保留提交，说明阻塞；不强制覆盖。

文档门禁工作流会检查文档和维护工具；产品工作流按路径决定运行前后端检查。开发分支单独推送不一定触发产品检查，合并请求或主分支结果才是对应证据。不要把“跳过”写成“通过”。

## 2. 双版本口径

| 用途           | 真值位置                                                                                                | 规则                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 经典版产品版本 | src/lib/classicVersion.ts（前端常量）与 src-tauri/src/commands/misc.rs（后端常量）                      | 两处必须同值；发布标签、关于页、更新比较与发布链接使用此版本 |
| 官方内核版本   | package.json（应用依赖清单）、src-tauri/Cargo.toml（后端包清单）、src-tauri/tauri.conf.json（桌面配置） | 跟随实际已集成内核；同时核对后端锁文件中的本包版本           |
| 产品发版增量   | 本次实际发布内容                                                                                        | 跟进内核才升次版本；未跟内核一律升补丁版本，即使包含新功能   |

读取桌面应用版本的通用接口返回的是内核版本，不能拿它拼产品发布标签。对外展示同时清楚区分产品与内核；主页徽标及正文不能各写一份互相矛盾的“当前版本”。

## 3. 打标签前逐项核对

- [ ] 已明确本次发版授权、目标提交与经典版版本；内核同步的完整审查记录已完成。
- [ ] 前端与后端两处产品常量同步；执行读取真实生产常量的守卫测试，不新增测试专用副本。
- [ ] 内核版本确实对应已集成代码；相关清单与锁文件一致。
- [ ] 按 [更新摘要说明](../../src/whats-new/README.md) 创建经典版版本文件，四语言完整，仅描述实际已发布的变化。
- [ ] CHANGELOG.md 已写「Classic（经典版）{版本}」小节：发布正文由 release.yml 从该小节生成（"### 本次更新"），缺失小节时发布流程直接失败。
- [ ] 更新主页版本徽标及正文中的版本信息；大范围变化补产品发布说明，保留历史上游发布说明的来源身份。
- [ ] 应用内发布链接使用经典版版本，可用更新链接使用目标更新版本；核对指向本项目。
- [ ] 获取远端主分支并复核内容，推送已验证提交；确认标签指向相同提交，再创建 v{产品版本}（产品版本标签）。

## 4. Windows 便携版边界

本独立维护分支仅构建 Windows x64 便携 ZIP。用户的单平台便携包要求取代原多平台安装器发布规则；其他平台的源码和常规 CI 测试不因此删除。

- `release.yml` 使用 `windows-2022` 和显式 `x86_64-pc-windows-msvc` 目标，运行 `pnpm tauri build --target x86_64-pc-windows-msvc --no-bundle -- --locked`。不执行安装器打包、不要求 Tauri 签名私钥、不生成 `.sig` 或 `latest.json`。
- 手动触发仅构建并上传 `windows-x64-portable` artifact，不创建 GitHub Release。推送 `v*` 标签才发布；标签必须与前后端 Classic 版本常量一致，并有更新摘要与 CHANGELOG 小节。
- 产物名称使用 Classic 版本常量，不使用可能含斜杠的分支名，也不使用内核版本。
- 应用下载、便携更新链接和发布说明指向 `yz0812/cc-switch-classic`。没有签名更新清单时，版本查询沿用 GitHub Releases API 回退；便携版通过下载 ZIP 更新。已有的签名校验机制不放宽。
- 当前流程不生成安装器。将来恢复安装版自动更新时，必须为本仓库配置独立签名材料、更新清单并验证更新链路；不得沿用他人的私钥或关闭签名校验。

## 5. 发布产物验收

- 只上传 `CC-Switch-Classic-v{classic}-Windows-Portable.zip` 一个文件，ZIP 根目录必须含 `cc-switch.exe` 与 `portable.ini`。
- 可执行文件不存在或为空时打包必须失败；不得上传历史缓存、用户配置或空包。
- 保留 `portable.ini` 使应用识别便携模式。运行环境需要 Microsoft Edge WebView2 Runtime，ZIP 不内嵌运行时安装器。
- 正式发布保持非预发布；手动打包仅作为构建验证。推送主分支不等于授权创建版本标签或发布版本。
- 验证打包脚本的成功与失败路径、最终 ZIP 内容、工作流对应的提交，以及真实 Windows 启动。仅有脚本夹具测试不能证明程序可启动。
